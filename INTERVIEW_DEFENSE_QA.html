1. Core React & Hooks Decisions

Q1: Why did you NOT use useEffect to store the filtered practitioner list in state?
English (Technical Explanation):

Filtered practitioners are a purely derived calculation from two existing sources of truth: the full practitioner list and the currently selected filter options. If I had stored the filtered list in a secondary useState and synced it via useEffect, React would perform an unnecessary secondary re-render every time filters change, opening the door to stale closures and out-of-sync race conditions. Calculating it directly during render is synchronous, deterministic, and aligns with UI = f(state).

Hinglish (Spoken in Interview):

"Sir, filtered list ek derived value hai jo original data aur selected filter criteria se compute hoti hai. Agar hum isko useEffect me setFilteredList(...) karte, toh component do baar re-render hota aur state sync ki wajah se bugs aate. Isliye maine render ke time direct filterPractitioners() pure function se derive kiya, jo React ka best practice hai."

Q2: Why did you wrap the sunrise fetch in AbortController inside useSunTimes?
English (Technical Explanation):

When a user switches observation nodes quickly, network latency varies. Without cancellation, the response for an earlier city might arrive after the response for a newer city, overwriting the UI with stale data. AbortController allows the cleanup function of useEffect to cancel the in-flight HTTP request as soon as coordinates change, guaranteeing that only the most recently requested city resolves.

Hinglish (Spoken in Interview):

"Sir, jab user fast-fast do ya teen cities switch karta hai, toh pichli request aur nayi request race condition me aa sakti hain. AbortController cleanup function me pichli pending request ko cancel kar deta hai taaki screen par hamesha aakhri select ki gayi city ka hi data dikhe."

Q3: Why did you avoid useMemo and useCallback in most components?
English (Technical Explanation):

Module 02 establishes that premature memoization adds overhead, code noise, and memory cost without measurable gain on a small dataset (12-15 records). Filtering 15 items in JavaScript takes less than 0.1ms. Tracking dependencies costs more than the computation itself. Default to clean standard functions unless profiling proves a bottleneck.

Hinglish (Spoken in Interview):

"Sir, Module 02 me saaf likha hai ki premature optimization se code noisy banta hai. 12-15 practitioners ko filter karne me 0.1 millisecond se bhi kam time lagta hai, isliye useMemo ka fayda hone ke bajaye dependency check ka ulta overhead hota. Jab tak measure na karein, unnecessary memoize nahi karna chahiye."

2. Next.js App Router Architecture

Q4: Why is layout.jsx a Server Component while page.jsx is a Client Component?
English (Technical Explanation):

The Next.js App Router rule is to keep 'use client' as far down the tree as possible. layout.jsx and [id]/page.jsx only render static layout structure and metadata. By keeping them Server Components, zero client JavaScript is sent to the browser for those shells. Conversely, page.jsx requires interactive state (city selector, event handlers), necessitating 'use client'.

Hinglish (Spoken in Interview):

"Sir, Next.js ka rule hai 'use client' ko tree me jitna neeche ho sake utna neeche rakhna. Root layout aur Detail page ko user interactivity ki zaroorat nahi thi, isliye unhe Server Component banaya taaki client par extra JavaScript na jaye. Jabki Home page me city picker tha jisko state chahiye thi, isliye use Client Component banaya."

3. API Resilience & The 4 Data States

Q5: Why check both response.ok AND json.status !== 'OK' on sunrise API?
English (Technical Explanation):

Because transport success does not equal domain success. The sunrise-sunset.org API returns HTTP 200 OK even when coordinates are invalid (e.g. lat=999), but includes { 'status': 'INVALID_REQUEST' } in the body. If my code only checked response.ok, it would attempt to parse results.sunrise and crash. Checking json.status !== 'OK' ensures proper error interception.

Hinglish (Spoken in Interview):

"Sir, sunrise-sunset.org API transport level par HTTP 200 bhejti hai chahe coordinates galat bhi ho, lekin response body ke andar { status: 'INVALID_REQUEST' } hota hai. Agar sirf response.ok check karte toh error catch nahi hota aur app crash kar jata. Isliye maine status code aur body status dono ko check kiya."

Q6: How do you differentiate between 'Empty' state and 'Error' state?
English (Technical Explanation):

A query returning zero results is a valid, successful outcome, not an error. Showing a red alert box for zero results confuses users. In my directory page, if filters match zero practitioners, the component renders a calm informational banner with a 'Show All Practitioners' action. It does not render a role='alert' box, which is reserved exclusively for actual network or calculation failures.

Hinglish (Spoken in Interview):

"Sir, zero results aana ek successful response hai, error nahi. Agar user ne aisa filter chuna jisme koi match na ho ([]), toh hum calm message dikhate hain aur filter reset karne ka option dete hain. Error state sirf tab aati hai jab actual me network tut jaye ya server fail ho jaye, jisme hum role='alert' aur Retry button dete hain."

4. Design Tokens & Pure CSS

Q7: Why use CSS Custom Properties instead of Tailwind or inline hex?
English (Technical Explanation):

Issue FRE-109 mandates pure CSS using design tokens. Tailwind introduces external build dependencies. By declaring tokens on :root in globals.css (--bg, --surface, --ink, --accent), the application achieves instant, zero-runtime theming. Component rules use only var(--token), ensuring zero raw hex values.

Hinglish (Spoken in Interview):

"Sir, onboarding manual aur issue FRE-109 ka contract tha ki hume design system ke tokens follow karne hain. Har color aur spacing :root ke CSS custom properties (var(--token)) se aani chahiye. Agar hum hardcoded hex code likhte toh dark mode me layout break ho jata, jabki CSS variables se OS dark mode aur toggle dono seamless chalte hain."

5. Testing Strategy & Behavior-Driven Testing

Q8: Why do your tests use getByRole rather than testing internal state?
English (Technical Explanation):

Testing implementation details (like inspecting state variables) produces brittle tests: if a developer refactors variable names without changing user behavior, the test fails. Following React Testing Library principles, tests interact with the rendered DOM exactly as an assistive technology or human user would: clicking buttons (getByRole('button')) and reading announcements (role='status', role='alert').

Hinglish (Spoken in Interview):

"Sir, Module 08 ka rule hai: user jo screen par dekhta hai wahi test hona chahiye, na ki internal state ya variable names. Agar hum variable ka naam badal dein lekin user ko output wahi mile, toh test pass rehna chahiye. Isliye maine getByRole aur getByLabelText use kiya hai jo real user actions ko test karte hain."

7. Deep-Dive Code Review Q&A (Hooks & Verification)

Q10: Why was abortControllerRef redundant in useSunTimes.js?
English (Technical Explanation):

In React's useEffect, the cleanup function returned by the effect runs automatically before every re-render and upon unmount. Calling controller.abort() in the cleanup function already cancels any in-flight request when the user switches cities. Storing AbortController in a useRef was redundant.

Hinglish (Spoken in Interview):

"Sir, useEffect ka cleanup function dependency change hone par automatically pichli request ko abort kar deta hai. Isliye useRef me alag se controller store karna redundant tha."

Q11: Why must setLoading(false) inside finally check !controller.signal.aborted?
English (Technical Explanation):

When a user switches cities quickly, in-flight requests are aborted. An aborted promise still executes its finally block. If setLoading(false) were called unconditionally, an aborted older request would prematurely turn off the loading indicator while the newer request is still running. Checking !controller.signal.aborted ensures only the active request manages loading state.

Hinglish (Spoken in Interview):

"Sir, jab user fast city change karta hai, cancelled request ka bhi finally run hota hai. Agar bina check kare setLoading(false) karenge toh loading premature band ho jayegi. Isliye !controller.signal.aborted zaroori hai."

Q12: Why did you construct the date using Asia/Kolkata timezone instead of toISOString()?
English (Technical Explanation):

toISOString() returns date in UTC. India operates on Asia/Kolkata (UTC+5:30). Between midnight and 5:30 AM IST, UTC is still in the previous calendar day. Intl.DateTimeFormat with Asia/Kolkata guarantees the date accurately matches Indian Standard Time.

Hinglish (Spoken in Interview):

"Sir, toISOString() date ko UTC me nikalta hai. India me raat 12 se subah 5:30 tak UTC me pichla din hota hai. Asia/Kolkata use karne se date hamesha correct Indian calendar day ke hisaab se banti hai."

Q13: Why do tests assert on accessible roles (getByRole) rather than exact text strings?
English (Technical Explanation):

Testing exact text strings couples test suites to marketing wording. If copy is updated, tests break unnecessarily. Asserting on accessible roles (role='status', role='alert', role='button') tests real user behavior and accessibility contracts according to WCAG.

Hinglish (Spoken in Interview):

Q15: Why does reading localStorage inside useState cause a hydration mismatch, and how did you solve it?
English (Technical Explanation):

During server-side pre-rendering (SSR), window is undefined, so the server renders the default city (Bengaluru: 12.9716). In the browser, if localStorage previously saved a different city (Delhi: 28.6139), reading it synchronously during initial useState causes the client's initial HTML to differ from the server HTML, triggering a React Hydration Mismatch. The fix is to initialize state with DEFAULT_CITY.id on both server and client, and synchronize the saved city from localStorage inside useEffect, which only executes after hydration is complete.

Hinglish (Spoken in Interview):

"Sir, SSR ke time server par localStorage nahi hota, isliye server default city (Bengaluru) render karta hai. Agar hum initial useState me localStorage read karenge toh client par Delhi aa jayega, jisse mismatch ho jayega. Fix ye hai ki useState me default rakho, aur localStorage ko useEffect me read karo kyunki useEffect hydration ke baad chalta hai."
